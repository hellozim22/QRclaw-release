## 1) 总体结论

方案方向正确，尤其是将铁律从“纯转发”重述为“中立中继”，并显式新增 C5“消息可回放”，有助于统一产品与工程叙事。  
但当前版本仍存在 **2 个阻塞风险** 与若干 **重大执行风险**，建议在进入 M1/M2 前完成文案与里程碑修订，避免 M3/M4 阶段出现口径冲突与高成本返工。

---

## 2) 风险清单（按严重度）

### 阻塞（Blocking）

1. **C2 文案与 M3 解密路径存在铁律级冲突**
   - 现状：`§1.3` 写“明文仅在端侧解密”，但 `§7.1/§7.2` 与 `§10 D2` 明确采用 Edge Function 统一解密。
   - 影响：会导致合规审查、实现验收与测试口径三套标准并存，属于“规范先天冲突”。
   - 涉及位置：`§1.3` L95；`§7.1` L480；`§7.2` L508-L510；`§10 D2` L663-L665。

2. **M3 缺少可执行灰度/回滚剧本，切换风险不可控**
   - 现状：M3 同时迁移 visitor 与 agent 历史到统一函数，缺“分阶段放量 + 明确回滚开关 + 观测阈值”。
   - 影响：线上延迟、解密失败、权限误判时只能“紧急回滚代码”，无预案开关。
   - 涉及位置：`§5.1` L331；`§8.1` L578；`§8.3` L611；`§7.2` L533-L539。

### 重大（Major）

3. **Owner 历史路径口径不一致**
   - 现状：文中同时出现 `get-decrypted-messages` 与“统一 `decrypted-messages`”两套说法。
   - 影响：团队可能各自实现“兼容保留”或“完全迁移”，导致接口漂移与测试难以收敛。
   - 涉及位置：`§1.3` L97；`§7.1` L476；`§10 D2` L663-L665。

4. **🟡“架构预留”与✅“MVP 必做”语义边界不够清楚**
   - 现状：L1.5/L1.6/L1.7 标注为🟡，但被放入 M1/M2 的 ✅里程碑出口；执行层面易被理解为“可做可不做”或“需要做完整行为”。
   - 影响：要么过度实现（提前做群聊行为），要么交付不一致（仅加字段未补抽象）。
   - 涉及位置：`§5.1` L325、L334-L337；`§8.1` L576-L577；`§10 D9` L723。

5. **`shared/contracts/` 在 M2 与 M3 卡片间存在隐性交叉 ownership**
   - 现状：M2-WS-OPT 与 M3-EDGE/M4-PLUGIN 都依赖或改动 contracts，但未指定唯一 owner 卡。
   - 影响：并行开发时高概率出现 export/barrel 冲突、重复 schema 或签名漂移。
   - 涉及位置：`§12.4.2` L976-L980；`§12.5.1` L1021；`§12.6.2` L1054。

### 可接受（Acceptable）

6. **D7/D8 砍功能导致“插件第一版弱能力”风险**
   - 现状：buttons/reactions/media/approvals/slash 全部移出 MVP。
   - 判断：对“先打通 channel”目标可接受，但需在 M4 增加“生态最小可用”验收场景，避免仅技术可用、产品不可用。
   - 涉及位置：`§10 D7` L692-L699；`§10 D8` L706-L714；`§6.2` L450。

## 3) 针对五个审查问题的结论

### Q1. §1.3 铁律重定义是否自洽（C1/C2/C5）

- **结论**：方向正确，但尚未完全自洽。  
- **肯定点**：
  - C1 从“纯转发”改为“中立中继”，成功解耦“内容中立”与“是否持久化”。
  - C5 新增后，回放能力从“隐式工程能力”升级为“显式产品承诺”。
- **主要问题**：
  - C2“明文仅端侧解密”与 D2“Edge Function 统一解密”冲突（阻塞项 #1）。
- **建议**：
  - 将 C2 技术实现改写为“平台不持久化明文；仅在授权读取路径短时解密并审计”。

### Q2. §5 & §6 中 MVP（✅）与预留（🟡）划分是否合理

- **结论**：总体合理，但需要收紧“预留粒度定义”。  
- **合理部分**：
  - 只预留 DB + optional field + fanout 抽象，避免 UI 与高层协议先行，符合“先最小可交付”。
- **风险部分**：
  - `fanout 抽象` 若在 M2 做成行为级改造，等 M5+ 真做 group/topic 时仍可能推倒。
- **建议**：
  - M2 的 L1.7 仅交付“接口抽象 + direct fast-path 封装 + 等价行为”，不引入新分发语义。

### Q3. §8 M3 统一 Edge Function 是否足够保守

- **结论**：当前不够保守。  
- **缺口**：
  - 缺“影子流量/双读比对”阶段；
  - 缺“量化阈值（p95、错误率）”；
  - 缺“路由级回滚开关”。
- **建议**：
  - 将 M3 拆为 M3a（新增+影子验证）/M3b（visitor 正式切换）；
  - 增加指标：`history_p95`、`edge_5xx_rate`、`decrypt_fail_rate`、`gateway_forward_fail_rate`；
  - 增加回滚：`HISTORY_READ_BACKEND=edge|legacy`。

### Q4. §10 D7/D8/D9 砍功能会不会“弱到没法用”

- **结论**：不会“没法用”，但会“偏窄场景可用”。  
- **判断依据**：
  - MVP 核心闭环（文本双向+流式+断线回放+多 agent+create-qrcode）已覆盖最小渠道能力。
- **建议**：
  - 在 M4 验收追加 3 个 OpenClaw 真实使用场景（长会话、重连恢复、双 token 并发），用“可用性证据”对冲功能瘦身风险。

### Q5. §12 Task Card 边界在 M2/M3 是否有隐形交叉

- **结论**：有，且集中在 `shared/contracts/` 与鉴权语义层。  
- **建议**：
  - 新增“Contracts Owner Card（唯一写权限）”；
  - 其他卡只通过 PR 依赖其产物，不直接改 contracts；
  - 在 Task Card 增加 `Owner` 字段，避免“Write-allowed 重叠即默认可改”。

## 4) 条款级修订建议（可直接回填文档）

1. **修订 C2 文案（强制）**
   - 位置：`§1.3` L95
   - 建议改为：平台仅持密文与元数据；明文仅在授权读取路径短时解密，且不得落盘，须可审计。

2. **统一 owner 历史路径**
   - 位置：`§1.3` L97、`§7.1` L476、`§10 D2`
   - 建议：明确“统一函数 + 兼容路由保留期（例如 1 个里程碑）”。

3. **M3 增加灰度与回滚章节**
   - 位置：`§7.2` 与 `§8.3 M3`
   - 建议新增：
     - 阶段 A：影子读比对（不对外切流）；
     - 阶段 B：10%→50%→100% 放量；
     - 失败即切回 legacy 路由。

4. **重述 L1.7 目标，避免过度实现**
   - 位置：`§5.1` L336，`§12.4.3`
   - 建议：强调“接口层抽象、行为不变、更换实现不更改语义”。

5. **Task Card 引入 owner 字段与仲裁机制**
   - 位置：`§12.1` 公共规范
   - 建议新增字段：
     - `Owner`（唯一负责目录）
     - `Conflict Resolution`（冲突由哪张卡决策）

## 5) M0–M4 边界与任务粒度建议

### 保持不变

- **M0**：文档与红线测试；不动代码。
- **M1**：DB 预留动作可继续推进。
- **M4**：插件 MVP 主体与发布链路。

### 建议调整

1. **M2 收敛**
   - 将 L1.7 细化为“抽象不改行为”；group/topic 行为实现明确后移 M5+。

2. **M3 拆分**
   - **M3a**：新增 agent history + `decrypted-messages` + 影子验证；
   - **M3b**：visitor 历史正式切流 + 观测达标后冻结 legacy。

3. **M4 增补可用性验收**
   - 增加“生态最小可用”场景化验收，不仅检查协议层连通。

## 6) 建议优先级与行动清单

### P0（进入 M1 前必须完成）

- 修正 C2 与 D2 的冲突文案（阻塞 #1）
- 明确 owner 历史统一策略（重大 #3）

### P1（进入 M2 前完成）

- 收紧 L1.7 的“抽象不改行为”定义（重大 #4）
- 在 §12 增加 contracts 唯一 owner 与冲突仲裁（重大 #5）

### P2（M4 验收前完成）

- 增加 3 个 OpenClaw 真实使用场景验收（可接受 #6）

---

## 7) 最终判定

当前方案 **可作为执行基础**，但不建议直接按现文进入 M1+。  
应先完成 P0 修订（铁律口径统一 + M3 风险治理）后再推进，以避免在“规范层冲突”未解决时进入实现阶段。
