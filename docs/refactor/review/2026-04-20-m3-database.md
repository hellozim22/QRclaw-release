## 2. Blockers (Correctness / Data Loss)

### B1 — Cursor pagination silently drops rows on `sent_at` ties

**File**: `supabase/functions/decrypted-messages/index.ts:346-354`  
**Severity**: BLOCKER  

**Scenario**: Two messages in the same conversation have identical `sent_at`
(same millisecond — realistic under WebSocket burst). The function paginates
with strict `<`:

```ts
query = query.lt('sent_at', cursorMsg.sent_at);
```

If the cursor points to message A at `2026-04-20T12:00:00.123Z` and message B
shares the same timestamp, the next page's `sent_at < '2026-04-20T12:00:00.123Z'`
excludes **both** A and B. Message B is permanently invisible to the client.

The `messages` table has no UNIQUE constraint on `(conversation_id, sent_at)`.
The `sent_at` column defaults to `now()` — concurrent INSERTs in the same
transaction or within the same millisecond produce ties.

**Fix**: Use a composite tiebreaker `(sent_at, id)`:
```sql
-- cursor resolution
SELECT sent_at, id FROM messages WHERE id = :cursor

-- page query
WHERE conversation_id = :cid
  AND (sent_at, id) < (:cursor_sent_at, :cursor_id)
ORDER BY sent_at DESC, id DESC
```
In Supabase JS this requires `.or()` with the equivalent filter, or a raw RPC.
Alternatively, the cursor can be `sent_at || '|' || id` encoded as a single
opaque string. The existing `idx_messages_conversation ON
messages(conversation_id, sent_at)` would need to become
`ON messages(conversation_id, sent_at DESC, id DESC)` for optimal range-scan
support.

**Parent instruction**: Add `id DESC` as tiebreaker to the cursor pagination in
`decrypted-messages/index.ts` and update the composite index to
`(conversation_id, sent_at DESC, id DESC)` via a new migration.

## 3. Highs

### H1 — No UNIQUE constraint on `encryption_keys (conversation_id) WHERE status = 'active'`

**File**: `supabase/migrations/20260312_init_schema.sql:234-236`  
**Severity**: HIGH  

The Edge Function calls `.single()` at line 321:
```ts
.eq('conversation_id', body.conversation_id)
.eq('status', 'active')
.single();
```

The existing `idx_encryption_keys_status` is a partial index
`ON encryption_keys(conversation_id, status) WHERE status = 'active'` — but it
is **not** a UNIQUE index. If a race in `upsertEncryptionKey`
(`gateway/src/db/persist.ts:18-68`) inserts two active keys for the same
conversation, `.single()` throws a Supabase `PGRST116` (more than one row)
and the entire history read fails.

**Scenario**: Two gateway instances simultaneously handle the first message for
the same conversation. Both run the "check DB for existing active key" SELECT
(line 27-33 of `persist.ts`), both get null, both INSERT. The function sees two
active rows → 500 error.

**Current mitigation**: The gateway's `pendingDEKs` map deduplicates per-process
but **not** across multiple gateway pods.

**Fix**: Add a partial unique index:
```sql
CREATE UNIQUE INDEX CONCURRENTLY idx_encryption_keys_unique_active
  ON encryption_keys(conversation_id)
  WHERE status = 'active';
```
This makes the second INSERT fail with a unique violation, which `persist.ts`
can catch and retry-with-select. The Edge Function `.single()` is then
guaranteed to return exactly 0 or 1 row.

**Parent instruction**: Add a partial UNIQUE index on
`encryption_keys(conversation_id) WHERE status = 'active'` in a new migration
and add conflict handling in `gateway/src/db/persist.ts`.

### H2 — Missing index on `agents.api_key_hash` — agent auth full table scan

**File**: `supabase/functions/_shared/auth.ts:97-101`  
**Severity**: HIGH (performance)  

`authenticateAgent` queries:
```ts
.from('agents')
.select('id, owner_id, status')
.eq('api_key_hash', keyHash)
.single();
```

There is **no index** on `agents.api_key_hash`. The `agents` table currently has
~10 rows, but the plan calls for multi-instance OpenClaw (many agents per
owner). Every agent history request triggers a sequential scan on an unindexed
TEXT column.

**Fix**:
```sql
CREATE UNIQUE INDEX CONCURRENTLY idx_agents_api_key_hash
  ON agents(api_key_hash);
```
The column is `NOT NULL` and hash values are inherently unique per key. A UNIQUE
index prevents duplicate hashes and eliminates the scan.

**Parent instruction**: Add a UNIQUE index on `agents(api_key_hash)` via a new
migration.

### H3 — Key rotation orphans historical messages (by design — but confirm intent)

**File**: `supabase/functions/decrypted-messages/index.ts:316-325`,
`gateway/src/crypto/key-manager.ts:163-168`  
**Severity**: HIGH (data accessibility)  

The Edge Function fetches only `status = 'active'` keys. If `rotateDEK` is
called (line 163 of key-manager.ts), the gateway generates a new DEK and
inserts a new active key — but the **old key's status is never changed** to
'revoked'. The `upsertEncryptionKey` in `persist.ts` only checks for existing
active keys and inserts if none found.

This means after rotation:
1. **If the old key is not marked 'revoked'**: H1 above triggers (two active
   keys → `.single()` crash).
2. **If the old key IS marked 'revoked' (future code path)**: messages encrypted
   with the old DEK become permanently unreadable because the function only
   fetches the active key.

**Current state**: `rotateDEK` is exported but **grep shows no caller** in the
commit diff or the existing codebase. It is dead code for now.

**Recommendation**: Either:
- (a) Remove the `rotateDEK` export to prevent accidental use until a proper
  rotation flow (that re-encrypts old messages or fetches all keys per
  conversation) is implemented.
- (b) Document that rotation intentionally makes old messages unreadable
  (crypto-shredding use case).

**Parent instruction**: Remove or gate `rotateDEK` to prevent use until the
Edge Function supports multi-key reads or re-encryption.

## 4. Mediums

### M1 — Owner authz returns 404 on missing conversation, leaking existence

**File**: `supabase/functions/decrypted-messages/index.ts:224-226`  
**Severity**: MEDIUM  

The owner path returns `404 not_found` when the conversation doesn't exist or
the join chain fails. The visitor path (line 278-279) deliberately returns `403`
to prevent existence oracles. The agent path also returns `404` (line 256).

**Issue**: An authenticated owner (or agent with a valid API key) can enumerate
conversation UUIDs by observing 404 vs 403 vs 401. This is a minor information
leak since UUIDs are 128-bit random, but the inconsistency with the visitor
path's explicit anti-enumeration comment suggests the author intended uniform
treatment.

**Fix**: Return `403 forbidden` for all "conversation not found or not yours"
cases across all actors, matching the visitor path's design intent.

**Parent instruction**: Unify the owner and agent 404 responses to 403 for
anti-enumeration consistency.

### M2 — `constantTimeEqual` length check leaks token length

**File**: `supabase/functions/decrypted-messages/index.ts:289-296`  
**Severity**: MEDIUM  

```ts
function constantTimeEqual(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  // ...
}
```

The early-return on length mismatch makes the comparison **not** constant-time
for unequal-length inputs. Session tokens are generated by the gateway and are
all the same length in practice, but if a custom visitor client sends a
different-length token, the timing difference is observable.

**Fix**: Pad or iterate over the longer string:
```ts
function constantTimeEqual(a: string, b: string): boolean {
  const len = Math.max(a.length, b.length);
  let mismatch = a.length ^ b.length;
  for (let i = 0; i < len; i++) {
    mismatch |= (a.charCodeAt(i) || 0) ^ (b.charCodeAt(i) || 0);
  }
  return mismatch === 0;
}
```

**Parent instruction**: Fix `constantTimeEqual` to iterate `max(a.len, b.len)`
so the length check itself is constant-time.

### M3 — Invalid cursor silently resets to first page

**File**: `supabase/functions/decrypted-messages/index.ts:346-355`  
**Severity**: MEDIUM  

When `body.cursor` is a UUID that doesn't exist in `messages`, the `.single()`
call returns null, and the `if (cursorMsg)` guard is skipped. The query then
executes without the `lt` clause, returning the **first page again**. The client
has no way to distinguish "no more pages" from "invalid cursor" — both return
data without error.

**Desired behaviour** (to be confirmed with product):
- Option A (strict): Return 400 `invalid_request` for a non-existent cursor.
- Option B (lenient, current): Reset to first page — acceptable if documented
  in the contract.

**Parent instruction**: Decide if invalid cursor should 400 or reset; add a
contract note either way.

## 6. Performance Notes

### P1 — Messages pagination index is adequate but not optimal

The existing `idx_messages_conversation ON messages(conversation_id, sent_at)`
covers the `WHERE conversation_id = ? ORDER BY sent_at DESC` pattern. PostgreSQL
can use a backward index scan on the B-tree, but a `DESC`-declared index
`ON messages(conversation_id, sent_at DESC)` would be more explicit and ~5%
faster for DESC scans on large conversations. If the tiebreaker fix (B1) is
applied, the index should be `(conversation_id, sent_at DESC, id DESC)`.

### P2 — Service-role bypass footprint

The Edge Function uses `getServiceClient()` (service role) for all 6 DB
queries. RLS is fully bypassed. The in-function authorization chains are the
sole access-control layer. This is necessary because the function serves three
different actor types with different auth mechanisms. However, it means any
logic bug in `resolveConversationAccess` is a direct data breach — there is no
defense-in-depth via RLS.

**Mitigation**: The authorization queries use `!inner` joins which enforce
non-NULL FK constraints at the query level. Combined with schema constraints
(`agents.owner_id NOT NULL`, `qrcodes.agent_id NOT NULL`), the chain is
structurally sound.

### P3 — No N+1 detected

The function makes exactly:
1. 1 auth query (owner JWT verify / agent hash lookup / visitor session match)
2. 1 authorization join query
3. 1 encryption key fetch
4. 0-1 cursor resolution query
5. 1 messages page query

Total: 3-5 queries per request. Decrypt is all in-memory. This is well within
acceptable bounds.

### P4 — Missing `agents.api_key_hash` index (see H2)

Every agent auth request does a sequential scan. Not a problem at 10 rows, but
will become one at scale.

## 7. Authorization Chain Audit (Detailed)

### Owner path

```
conversations.id → qrcodes!inner(agents!inner(owner_id, owners!inner(user_id)))
```

- `agents.owner_id` is `UUID NOT NULL` — the `!inner` join is safe; no row with
  NULL owner_id can match.
- `owners.user_id` is `UUID NOT NULL UNIQUE` — exactly one owner per auth user.
- **Ownership transfer**: If `agents.owner_id` is updated (e.g. transfer), the
  old owner immediately loses access because the join chain resolves to the new
  owner's `user_id`. No history leakage.
- **Multi-owner**: Not possible — `agents.owner_id` is a single FK, not a join
  table. One agent = one owner.

**Verdict**: SOUND.

### Agent path

```
conversations.id → qrcodes!inner(agent_id)
```

- `qrcodes.agent_id` is `UUID NOT NULL` — one agent per QR code.
- No `!inner` on the agent itself is needed since `agent_id` is fetched as a
  column, not a join.
- **Cross-agent leak**: Impossible. `qrcodes.agent_id` is scalar; one QR code
  maps to exactly one agent. If agent A creates QR code X, only agent A can
  read conversations on X.

**Verdict**: SOUND.

### Visitor path

- Fetches `conversations.session_token` by primary key `id`.
- Constant-time compares `session_token` to the body value.
- Returns 403 on both "not found" and "mismatch" — no existence oracle.
- **Edge case**: `conversations.session_token` is `TEXT NOT NULL`, so `String(data.session_token)` never coerces undefined/null.

**Verdict**: SOUND (modulo M2 length-leak in `constantTimeEqual`).
