### MEDIUM

#### M-1: `decrypted-messages-client.ts:72` — Service-role key as `apikey` header fallback

**File**: `gateway/src/services/decrypted-messages-client.ts:72`

```typescript
const apikey = env.SUPABASE_ANON_KEY || env.SUPABASE_SERVICE_ROLE_KEY;
```

**Risk**: If `SUPABASE_ANON_KEY` is unset but `SUPABASE_SERVICE_ROLE_KEY` is present, the service-role key is sent as the `apikey` header (and also as the `Authorization: Bearer` header for visitor requests, line 96). The `apikey` header travels over HTTPS to the Supabase gateway, which is expected, but:

1. The service-role key grants **full admin access** to the Supabase API (bypasses RLS). If the edge function is ever misconfigured or a man-in-the-middle gains TLS position, the attacker gets admin rather than anon.
2. The `Authorization: Bearer <service-role-key>` on visitor calls means the Edge Function's `authenticateOwner()` path would succeed for any user if an attacker replayed the same request with `actor: 'owner'` — the Supabase `getUser()` call with a service-role token returns the service user context. (In practice the owner authz chain then compares `user_id` so this doesn't directly bypass authz, but it widens the blast radius of an intercepted request.)

**Exploit scenario**: Gateway deployed with `SUPABASE_ANON_KEY=""` (misconfiguration) → service-role key sent in clear-text `apikey` header on every visitor history request → intercepted key gives full DB admin.

**Fix**: Fail closed when `SUPABASE_ANON_KEY` is missing rather than falling back to the service-role key. The service-role key should never leave the gateway's server-side Supabase client.

```typescript
const apikey = env.SUPABASE_ANON_KEY;
if (!url || !apikey) {
  return { ok: false, error: { code: 'service_unavailable', ... } };
}
```

**One-liner for parent**: In `gateway/src/services/decrypted-messages-client.ts:72`, remove the `|| env.SUPABASE_SERVICE_ROLE_KEY` fallback so only the anon key is used as the apikey header.

#### M-2: `constantTimeEqual` early-returns on length mismatch (timing side-channel on token length)

**File**: `supabase/functions/decrypted-messages/index.ts:289-296`

```typescript
function constantTimeEqual(a: string, b: string): boolean {
  if (a.length !== b.length) return false;   // ← early return
  let mismatch = 0;
  for (let i = 0; i < a.length; i += 1) {
    mismatch |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return mismatch === 0;
}
```

**Risk**: The length check on line 290 exits immediately when lengths differ. An attacker who can measure sub-millisecond response-time differences can determine the **length** of `data.session_token` (the database value). Session tokens are typically UUIDs (36 chars), so the information leak is minimal in practice — the attacker already knows the expected format. However, it violates the principle of the function's name.

**Practical impact**: LOW for UUID-length tokens. Would be HIGH if session tokens were variable-length secrets.

**Fix**: Pad the shorter string to the longer length and always iterate `max(a.length, b.length)` bytes, or use a fixed-length comparison (e.g., always compare 64 bytes with padding). The simplest idiom:

```typescript
function constantTimeEqual(a: string, b: string): boolean {
  const maxLen = Math.max(a.length, b.length);
  let mismatch = a.length ^ b.length;          // non-zero if lengths differ
  for (let i = 0; i < maxLen; i += 1) {
    mismatch |= (a.charCodeAt(i) || 0) ^ (b.charCodeAt(i) || 0);
  }
  return mismatch === 0;
}
```

**One-liner for parent**: In `supabase/functions/decrypted-messages/index.ts:289-296`, replace `constantTimeEqual` with a version that iterates `max(a.length, b.length)` and XORs lengths into the mismatch accumulator to eliminate the early-return timing side-channel.

### LOW

#### L-1: `hexToBytes` accepts non-hex characters silently

**File**: `supabase/functions/_shared/crypto/hex.ts:6-14`

`parseInt(hex.substring(i, i+2), 16)` returns `NaN` for non-hex input (e.g. `"zz"`). `NaN` is coerced to `0` when stored in a `Uint8Array`. This means a malformed `key_data_encrypted` value could silently produce a zeroed-out byte array instead of throwing, which would cause a GCM auth-tag failure downstream (Web Crypto throws `OperationError`). The failure mode is correct (decrypt fails, returns sentinel), but the error message would be misleading ("GCM decryption failed" rather than "invalid hex in DEK").

**Fix**: Add a `NaN` check or a pre-validation regex (`/^[0-9a-fA-F]*$/`).

**One-liner for parent**: In `supabase/functions/_shared/crypto/hex.ts:hexToBytes`, add a `/^[0-9a-fA-F]*$/` pre-check or post-parseInt NaN guard so invalid hex throws immediately rather than producing silent zero bytes.

#### L-2: Outer catch logs raw error object for non-Error throws

**File**: `supabase/functions/decrypted-messages/index.ts:89`

```typescript
console.error('decrypted-messages error:', err instanceof Error ? err.message : err);
```

If a dependency throws a non-Error value that happens to contain key material (e.g., a string interpolation that includes env vars), the raw value goes to structured logs. The `err.message` branch is safe, but the fallback `err` branch serialises the thrown value directly.

**Practical impact**: Very low — dependencies in this call graph throw `Error` subclasses. But defensive logging should `String(err)` at minimum.

**Fix**: Replace `err` with `String(err)` in all three `console.error` fallback branches (lines 89, 332, 432).

**One-liner for parent**: In `supabase/functions/decrypted-messages/index.ts`, replace the three `err instanceof Error ? err.message : err` patterns with `err instanceof Error ? err.message : String(err)` to prevent raw object serialisation in logs.

#### L-3: `globalThis.__QRCLAW_KEK_LEGACY_WARNED__` flag — negligible prototype-pollution surface

**File**: `gateway/src/crypto/key-manager.ts:32-36,43-46`

The `declare global` + `globalThis.__QRCLAW_KEK_LEGACY_WARNED__` pattern is safe in Node.js — `globalThis` is a native object whose prototype is `Object.prototype`, and the property is only set to `true`. A prototype-pollution attack that plants `__QRCLAW_KEK_LEGACY_WARNED__ = true` on `Object.prototype` would only suppress the deprecation warning — no security impact.

**Verdict**: Acknowledged, no action needed.

## 5. Observations & Positives

1. **Trust-boundary narrowing is real and well-executed.** The gateway can no longer reconstruct plaintext even if fully compromised — the KEK never enters the Node process, and `decrypt`/`decryptDEK` are gone from the codebase. This is a material improvement to Iron Rule C2.

2. **Per-row decrypt failure sentinel.** `[decryption_failed]` / `[decryption_unavailable]` means one corrupt row can't black-hole an entire page of messages. This is a good resilience pattern.

3. **Privacy-preserving error mapping.** The gateway collapses `forbidden`, `not_found`, and "no conversation" into `200 empty` — no existence oracle for session_tokens or conversation_ids. The test on line 187 (`expect(JSON.stringify(payload)).not.toContain('sess-secret')`) explicitly guards against session_token leakage.

4. **Strict body parsing.** The Edge Function's `parseBody` manually validates every field with type checks and anchored UUID regex rather than relying on Zod (which isn't mirrored to Deno). The validation covers `typeof`, enum membership, `Number.isInteger`, and range bounds.

5. **Identical error responses for not-found vs. wrong-token** in the visitor path (line 277-283) prevent conversation-ID enumeration.

6. **Cross-runtime parity test** (`tests/unit/shared/supabase-crypto-port.test.ts`) feeds real gateway `encrypt()` output into the Deno crypto module — this locks the wire format and catches drift between the two runtimes.

7. **SHA-256 on API keys** before DB lookup is the correct pattern — it eliminates timing oracle on the raw key (hash preimage resistance makes timing irrelevant at 2^128 security level).

8. **AbortController timeout** on the gateway client with explicit `clearTimeout` and separate error codes for `timeout` vs. `network_error` — good observability without leaking internals.
